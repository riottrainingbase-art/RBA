## 2. 本番RBAの運用
1. Stripeで支払成功が確認され、署名付きWebhookが一意な注文IDをDBに登録した状態のみを**入金済・受注**とする。
2. RBAだけが支払/顧客照合、注文番号、品番・色・サイズ・数量・合計価格を管理する。顧客住所などはStripeの管理範囲に残す。
3. RBAが必要な製造指図（注文番号・SKU・サイズ・数量・ロゴ加工内容・納期）だけを製造先へ渡す。顧客情報は履行に必要な最小限だけ、契約・適切な取り扱いの範囲で別途共有する。
4. 製造先の受理を確認して `accepted_by_production`、素材確認後 `materials_ready`、加工中 `making`、検品 `quality_check`、梱包 `packed`、実発送証跡後 `shipped`、配達証跡後 `delivered` にRBAが更新。問題時 `problem` を先に登録。
5. 発送は実際の追跡番号・配送会社・発送日が揃った後だけ記録。送信サービスの受理と購入者の受信を混同しない。
6. 返金はRBAだけが取引IDと返金条件を照合して実行。Stripe・台帳の両方で証跡確認。入金後の受注不成立・欠品・出荷不能を隠さない。
7. 領収/納品・発送・返品問い合わせの受付経路を一元化。顧客の健康情報や不要な個人情報を製造台帳に残さない。

## 4. 初期7日間の販促と検証（開始日は実公開日を起点）
- Day 0：本番トップ・商品ページ・モバイル・価格・最終確認・返品と特商法を確認。購入者に「予約確定」誤認を生まない。
- Day 1：公式InstagramでFIRST DROPのコンセプトと2商品、メーカー仕様とCG注記を紹介。**在庫僅少や売切れ間近を根拠なく主張しない。**
- Day 2：ストーリーでTシャツの素材・サイズ、リンクは公式ストア/無料案内の状態に合わせて選択。
- Day 3：上下セットの実物形状とCGとの差異を説明。
- Day 4：発送・返品・価格のFAQ、RBA管理の受注・売上の透明性を紹介。
- Day 5：既存の同意がある会員/クリニック参加者へ公式LINE経由で1回案内。Torsten送信禁止対象は除外。未同意者への広告一斉送信はしない。
- Day 6：返信・質問を匿名集計しサイズや価格説明を改善。
- Day 7：フォーム登録数、商品別希望数、販売開始後の購入件数、未発送注文・返金件数・履行遅延の有無を照合。公開前の登録者は注文済み扱いしない。

## 5. 管理KPI（初期値を創作しない）
| 指標 | 定義 |
| --- | --- |
| 登録数 | Jotform実送信レコード数。未送信・重複を除く |
| 購入希望数量 | 商品ごとの希望数量合計。実売上に計上しない |
| CVR | Stripeで支払成功した一意注文数 ÷ 実際の決済ページ訪問者数 |
| 売上 | RBA Stripeで入金成功した取引の合計。未決済の希望数を含めない |
| 粗利/利益 | 売上 − 原価/加工/送料/手数料/返品等（要税務整理） |
| 発送履行 | 期限内発送数 ÷ 当該期限の有料注文数 |
| 返品・返金 | 実際の返品/返金処理IDと理由の件数。申出と返金済みを区別 |

**外部SNS案内、予約発注、支払・返金の自動実行はこの文書を作成したことでは起動しない。**
